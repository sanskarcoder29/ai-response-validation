## 1. Problem statement

Large Language Models (LLMs) can generate fluent responses that are inaccurate, incomplete, irrelevant, unsupported, or contradicted by available evidence.

This project aims to develop a modular AI response validation system that accepts a question and an AI-generated response, retrieves relevant reference material, evaluates the response across defined quality dimensions, and eventually produces an explainable verdict supported by evidence.

Milestone 1 establishes the research, architecture, input and storage foundation, and reference retrieval capability required for later automated evaluation.

## 2. Research summary — M1.1

### 2.1 LLM evaluation

LLM evaluation measures the quality and reliability of responses generated by language models. Evaluation can combine reference-based metrics, reference-free model judging, and task-specific checks.

**Reference-based evaluation** compares a generated response with a known answer, labelled example, or trusted source.

**Reference-free evaluation** uses an explicit rubric or judge model to assess qualities such as relevance, clarity, or completeness when an exact reference answer is unavailable.

Automated evaluation should be checked against human-reviewed examples because model judges can be inconsistent, biased, or prompt-sensitive.

### 2.2 Hallucination detection and factuality

For this project, hallucination is treated operationally as a substantive claim that is unsupported by, or contradicted by, the evidence available to the evaluator.

The proposed system should break a response into claims and classify each claim as:

- **Supported:** the available evidence supports the claim.
- **Contradicted:** the claim conflicts with the available evidence.
- **Insufficiently evidenced:** the available evidence is not enough to verify the claim.

Lack of evidence is not automatically proof that a claim is false. The system must distinguish unsupported information from information directly contradicted by reliable evidence.

### 2.3 Faithfulness and relevance

**Faithfulness** concerns whether the answer is supported by the retrieved reference context.

**Relevance** concerns whether the answer addresses the user's question.

A response can be relevant but unfaithful: it may discuss the correct topic while making unsupported claims. A response can also be faithful to one retrieved passage but incomplete for the original question.

Both dimensions are important for reliable AI response validation.

### 2.4 Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation separates reference-data ingestion from query-time retrieval.

The proposed retrieval workflow includes:

1. Cleaning and preprocessing reference documents.
2. Splitting reference material into manageable chunks.
3. Generating numerical embeddings for the chunks.
4. Storing embeddings with their associated metadata.
5. Converting a search query into an embedding.
6. Retrieving semantically similar reference chunks.
7. Packaging retrieved passages as evidence for later evaluation.

Retrieval quality must be measured. Poor retrieval can make a correct answer appear unsupported or can provide misleading evidence.

The Milestone 1 prototype implements benchmark preprocessing, chunking, embedding generation, local vector storage, cosine-similarity search, and evidence-context construction.

### 2.5 Embeddings and vector similarity

An embedding is a numerical representation of text. Texts with similar meanings can have similar vector representations even when they use different words.

The prototype uses cosine similarity to compare a query vector with stored reference vectors. Results are ranked by similarity. A similarity score is a ranking signal; it is not a calibrated probability that a passage is correct or relevant.

### 2.6 LLM-as-a-Judge

LLM-as-a-Judge prompts a model to assess an output against explicit criteria and return structured scores or explanations.

The proposed design separates judge responsibilities into relevance, accuracy, hallucination detection, and completeness. Judge outputs should use a fixed schema, cite evidence identifiers, and be calibrated against human-labelled examples.

A judge model is itself fallible, so its verdict is an aid to review rather than ground truth.

**Implementation status:** Judge agents, automated scoring, and verdict generation are proposed for later milestones. They are not implemented in the current Milestone 1 prototype.

### 2.7 Framework review: RAGAS and TruLens

- **RAGAS:** A framework for evaluating retrieval-augmented generation systems. Its metric catalogue includes concepts such as faithfulness, response relevancy, context precision, context recall, and factual correctness.
- **TruLens:** A framework for instrumenting and evaluating LLM applications. Its concepts include context relevance, groundedness, and answer relevance.
- **Initial decision:** Both frameworks were studied. The initial prototype uses a small, explicit project rubric. Selected RAGAS or TruLens metrics may be considered in later milestones. Neither framework is currently integrated into the runtime.

### 2.8 Benchmark datasets studied

**TruthfulQA** provides misconception-oriented questions and reference answers. It is useful for studying truthfulness and common misconceptions.

**SQuAD (Stanford Question Answering Dataset)** provides questions associated with passages and answer spans. It is useful for question-answering and reference-passage retrieval experiments.

See `DATASETS.md` for dataset identifiers, acquisition details, attribution information, and processing counts.

## 3. System architecture — M1.2

The system is designed as a modular application with separate responsibilities for user input, backend processing, submission storage, reference ingestion, retrieval, and future response evaluation.

See `ARCHITECTURE.md` for the architecture diagrams, component responsibilities, data flows, proposed data models, and open design questions.

The proposed architecture contains:

1. User interface and backend API.
2. Submission validation and storage.
3. Reference dataset ingestion and preprocessing.
4. Embedding generation and vector indexing.
5. RAG retrieval and evidence packaging.
6. Evaluation orchestrator and specialised judge agents.
7. Score aggregation, verdict, and report presentation.

The current implementation covers the input and storage foundation and the reference retrieval workflow. The automated evaluation and verdict components remain future work.

## 4. Proposed agent responsibilities

The following are architecture responsibilities for future milestones, not implemented agents.

- **Evaluation Orchestrator:** Coordinates the evaluation workflow, assembles the submission and evidence package, invokes judge components, and tracks execution status.
- **Relevance Judge Agent:** Checks whether the response addresses the original question without drifting off topic.
- **Accuracy Judge Agent:** Checks factual claims against a reference answer or trusted evidence.
- **Hallucination Detection Agent:** Identifies unsupported and contradicted claims and associates findings with evidence references where possible.
- **Completeness Judge Agent:** Checks whether the important aspects of the question and reference are addressed.
- **Verdict Agent:** Aggregates structured outputs, applies approved thresholds and evidence guardrails, and returns a proposed verdict such as PASS, NEEDS_REVIEW, or FAIL.

These agent interfaces and responsibilities require further design, mentor feedback, and implementation in subsequent milestones.

## 5. Proposed scoring dimensions

The initial proposed rubric uses four dimensions, each scored from 1 to 5:

| Evaluation dimension | Proposed weight |
|---|---:|
| Relevance | 20% |
| Accuracy | 30% |
| Hallucination safety | 30% |
| Completeness | 20% |

Higher scores are better for every dimension.

The weights and thresholds are provisional. They require mentor review and empirical calibration against human-reviewed examples before being used for automated evaluation.

**Current implementation status:** The rubric is documented. Automated score calculation and verdict generation are not implemented.

## 6. M1.3 — Evaluation Input Module

The current implementation provides the initial input and submission-storage functionality.

### 6.1 Implemented components

- Streamlit form for entering the required question and AI-generated response.
- Optional reference answer and pasted source/reference material.
- FastAPI backend for receiving submissions.
- Pydantic request validation, including required-field checks and configured length limits.
- SQLite persistence with a generated submission ID and UTC timestamp.
- FastAPI interactive API documentation through `/docs`.

### 6.2 API endpoints

**GET `/health`**
Checks whether the backend service is running.

**POST `/submissions`**
Validates and stores an evaluation submission. Successful submission storage was previously verified with an HTTP 201 response.

**POST `/knowledge-base/search`**
Accepts a search query and retrieves candidate reference passages from the local reference vector database. Retrieved passages are candidate evidence and still require evaluation.

### 6.3 Current boundary and limitations

The input module validates and stores submissions, and the retrieval endpoint provides reference passages. It does not yet run the judge agents, calculate hallucination scores, or produce an automated verdict.

Optional source material is currently supplied as pasted text. A complete PDF/DOCX upload and document-parsing pipeline is not implemented.

### 7.2 Chunking strategy

The current chunking configuration is:

- Chunk size: 500 characters.
- Overlap: 100 characters.

Chunk metadata preserves the dataset name, source record identifier, chunk identifier, chunk index, and original reference information.

Combined chunk data is stored in `data/processed/reference_chunks.json`.

### 7.3 Embedding generation

The prototype uses Google's Gemini Embedding 2 model.

- Model: `gemini-embedding-2`
- Embedding dimensions: 3,072
- Total reference chunks: 2,235
- Successfully generated embeddings: 2,235
- Remaining chunks: 0

Embeddings are stored in `data/processed/reference_embeddings.jsonl`. The generation script saves successful embeddings individually and skips previously completed valid chunk IDs. The configured maximum for future new batches has been restored to 250 per execution.

### 7.4 Vector storage and indexing

The local SQLite vector database is:

`data/processed/reference_vectors.db`

The index contains 2,235 unique chunk-ID records:

- TruthfulQA: 892 records.
- SQuAD: 1,343 records.
- Vector dimensions: 3,072.

The database stores reference text, metadata, embedding vectors, and vector norms. NumPy is used for cosine-similarity calculations and ranking.

### 7.5 Retrieval implementation

The active retrieval workflow:

1. Validates a natural-language query.
2. Generates a fresh query embedding using Gemini Embedding 2.
3. Loads stored reference vectors from SQLite.
4. Calculates cosine similarity using NumPy.
5. Ranks candidate passages.
6. Filters repeated normalized passage text from the returned result list.
7. Returns ranked passages with similarity scores and metadata.
8. Prepares labelled evidence context for subsequent evaluation components.

The query-embedding step requires an external Gemini API request. Local SQLite search, deduplication, and context construction do not require an external API request.

### 7.6 SQuAD duplication audit and mitigation

An audit of the 1,343 SQuAD chunks using whitespace-normalized, case-insensitive text found:

- Total SQuAD chunks: 1,343.
- Unique normalized text chunks: 196.
- Duplicate groups: 194.
- Extra duplicate chunks: 1,147.

The observed cause is that multiple SQuAD question records can share the same source context, while the current chunking script processes each record separately and assigns record-specific chunk IDs.

A retrieval-layer correction now suppresses repeated normalized passages in returned search results. Where duplicate passages are grouped, associated record IDs, questions, and reference answers are retained in the result metadata.

**Important limitation:** This correction deduplicates returned search results only. The original chunk JSON, embedding JSONL, and SQLite database still contain the repeated SQuAD records. Source-level deduplication—chunking each unique context once while preserving all associated question and answer metadata—is a future improvement.

### 7.7 Initial live semantic retrieval checks

Two initial natural-language retrieval examples were tested using fresh Gemini query embeddings.

**TruthfulQA example**

- Query: “What happens to watermelon seeds after a person eats them?”
- Expected reference: the watermelon-seed question and its best answer.
- Retrieved matching reference: Rank 1.
- Similarity score: `0.828731`.
- Dataset: TruthfulQA.

**SQuAD example**

- Query: “What is located immediately behind the Basilica of the Sacred Heart?”
- Relevant retrieved passage: the Grotto is immediately behind the Basilica.
- Retrieved rank: 2.
- Similarity score: `0.690037`.
- Dataset: SQuAD.

These examples demonstrate that the query-embedding and local retrieval path can retrieve relevant references from both datasets. They are initial functional checks, not a statistically representative retrieval-quality evaluation. Similarity scores are ranking signals, not calibrated confidence percentages.

## 10. Risks and limitations

- Vector similarity is not factual verification. A retrieved chunk may be similar without directly supporting the answer.
- The benchmark pilot does not cover every domain or current fact.
- The SQuAD pilot contains substantial repeated text; result-level filtering is implemented, but source-level deduplication remains pending.
- Only two live semantic retrieval examples have been manually inspected. Broader evaluation on a labelled question set is still required.
- Gemini query embedding depends on external API availability and free-tier quotas.
- LLM judges may be biased, inconsistent, or prompt-sensitive.
- Accuracy cannot be assessed confidently when reliable reference evidence is missing; an insufficient-evidence state should be supported.
- Full PDF/DOCX upload, extraction, and parsing are not implemented.
- Automated judge agents, scoring, orchestration, and verdict generation are future components.
- Dataset licensing and attribution requirements are separate from the project's source-code licence.
